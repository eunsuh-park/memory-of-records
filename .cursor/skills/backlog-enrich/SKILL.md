# Backlog 점검 · 그룹핑 · 구체화 (스킬 2)

`Backlog.md`를 읽고 **비슷한 기능끼리 묶고**, 각 항목의 실질 내용을 **더 구체적으로** 채운다.
문장만 늘리지 않는다. 구현 관점의 빈칸(화면, 상태, 예외, 데이터)을 메운다.

## 언제 쓰는가

- 「Backlog 정리해 줘」「비슷한 것 그룹핑」
- 「내용 보충해」「구체화해」「enrich」
- Inbox가 길어서 구조가 필요할 때

## 핵심 원칙

1. **간소화 금지.** bullet을 합쳐 짧게 만드는 것이 목표가 아니다. 정보량을 줄이지 않는다.
2. **구체화.** 각 항목에 아래를 가능한 한 채운다 (모르면 `미정 — 확인 필요`로 남긴다).
   - 목적 (누가 / 무엇을 / 왜)
   - 대상 화면·컴포넌트 (예: Jukebox, NoteImageViewer, AddPageModal)
   - 동작 시나리오 (기본 / 예외 / 빈 상태)
   - 데이터·API·권한 (있으면)
   - 디자인·UX 메모 (사용자가 디자이너임을 고려해 시각·인터랙션 힌트)
   - 열린 질문
3. **그룹핑.** 유사 주제끼리 `##` 섹션으로 묶는다. Inbox에 있던 원문은 그룹 안으로 **옮겨** 보존한다 (삭제처럼 보이게 버리지 말 것).
4. **원문 추적.** 각 항목에 `(수집 YYMMDD)`와 가능하면 원문 메모를 유지한다.
5. **우선순위는 아직 확정하지 않는다.** P0/P1 표기는 `backlog-to-roadmap` 스킬에서 한다. 여기선 기껏해야 「관련도」만 표시.

## 권장 섹션 구조

파일을 재구성할 때 대략 이 형태를 쓴다 (프로젝트에 맞게 이름 조정 가능).

```markdown
# Backlog

> 마지막 enrich: YYMMDD
> Inbox 잔여: N개 (미분류면 ## Inbox 유지)

## 그룹: {주제명}
<!-- 예: 공유·URL, 업로드·미디어, 네비·필터, 뷰어·레이아웃, 계정·공개범위 -->

### {기능 제목} `(수집 YYMMDD)`
- 상태: backlog
- 목적: …
- 화면/진입: …
- 시나리오:
  - 기본: …
  - 예외: …
- 데이터/API: …
- 디자인·UX: …
- 열린 질문: …
- 원문 메모: …

## Inbox
<!-- enrich 후에도 애매한 것만 남김 -->
```

## 작업 절차

1. `Backlog.md` 전체를 읽는다. 없으면 사용자에게 capture 스킬부터 쓰라고 안내한다.
2. 주제를 나열해 그룹 후보를 정한다 (3~8개 권장).
3. 항목을 그룹으로 재배치하고, 각 항목을 위 필드로 **보충**한다.
4. 불확실한 내용은 추측으로 확정하지 말고 `열린 질문`에 적는다.
5. 상단에 `마지막 enrich: YYMMDD`를 갱신한다.
6. 사용자에게: 생긴 그룹 목록 + 보충하며 생긴 질문만 짧게 보고한다.

## 하지 말 것

- 「정리」명목으로 요구사항 삭제·병합해 흐리기
- Roadmap.md를 이 스킬에서 새로 만들거나 완료 처리하기
- 코드 구현 시작 (명시적으로 「이어서 구현」이 있을 때만)
