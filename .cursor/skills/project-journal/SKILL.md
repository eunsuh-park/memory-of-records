# 프로젝트 일지 (스킬 4)

Roadmap 작업을 진행하는 동안의 **프롬프트·결정·배움**을 일지로 남긴다.
사용자는 **디자이너**다. 엔지니어링 용어를 남발하지 말고, 디자인·제품 관점의 배움을 분명히 적는다.

## 언제 쓰는가

- 「일지 써 줘」「저널」「오늘 작업 정리」「회고」
- Roadmap 항목을 하나 끝낸 뒤
- 마일스톤·페이즈가 바뀔 때
- 긴 디버깅/디자인 탐색 후 학습을 남길 때

## 저장 위치 · 파일명

- 폴더: `docs/journal/` (없으면 생성)
- 파일명: `YYMMDD_{작업 및 마일스톤 혹은 페이즈명}.md`
  - 예: `260812_노트_slug_공유.md`, `260812_Favorites_네비.md`
  - 공백 대신 `_`, 한글·영문 모두 가능. 너무 길면 핵심어 3~6개로 자른다.
- **같은 날 같은 주제**면 기존 파일에 섹션을 추가한다. 주제가 다르면 새 파일을 만든다.

## 일지 작성 관점 (디자이너)

반드시 포함할 것:

1. **오늘/이번 작업에서 다룬 화면·흐름** (제품 언어)
2. **몰랐던 것** — 개념, 제약, 플랫폼 한계, 협업(개발) 용어 등
3. **새로 알게 된 것** — 왜 그렇게 동작하는지, 다음에 디자인할 때 쓸 힌트
4. **결정과 이유** — 선택한 UI/우선순위, 버린 대안
5. **아직 모호한 것** — 다음 확인 질문

개발 구현 디테일(파일 경로 나열)은 짧게. 「무엇이 사용자에게 달라졌는지」가 본문이다.

## 템플릿

```markdown
# {작업 및 마일스톤 혹은 페이즈명}

- 날짜: YYMMDD
- 관련 Roadmap: {항목 제목 또는 없음}
- 관련 Backlog: {있으면}

## 한줄 요약

…

## 다룬 것

- …

## 결정

- 결정: …
  - 이유: …
  - 대안: …

## 몰랐던 것

- …

## 새로 알게 된 것

- …

## 화면에 남은 변화

- …

## 다음에 확인할 것

- …

## 참고한 대화·프롬프트 메모

> 사용자 요청에서 중요했던 문장·제약만 인용 (민감 정보 제외)
```

## 작업 절차

1. 현재 대화에서 Roadmap/Backlog 관련 요청·피드백·수정 지시를 수집한다.
2. `Roadmap.md` 진행 로그·최근 코드 변경이 있으면 사실 확인용으로만 참고한다.
3. `docs/journal/`에 규칙대로 파일을 만들거나 이어 쓴다.
4. 디자이너 톤으로 **몰랐던 것 / 새로 알게 된 것**을 비우지 않는다. 대화에 명시가 없으면, 이번 작업에서 드러난 개념 갭을 추론해 적고 `(추정 — 확인 필요)`를 붙인다.
5. 사용자에게 일지 경로만 짧게 알린다.

## Roadmap과의 연결

- Roadmap 항목을 `done`으로 닫을 때 이 스킬을 **함께** 쓰는 것을 권장한다 (`backlog-to-roadmap` 완료 보고 직후).
- 일지 파일명·한줄 요약을 Roadmap 진행 로그에 한 줄로 링크해도 된다.

## 하지 말 것

- 엔지니어 커밋 로그를 그대로 붙여 넣은 「가짜 일지」
- 학습 섹션을 비운 채 작업 목록만 나열
- `docs/journal` 밖의 임의 경로에 저장
- 사용자가 일지를 거부했는데 자동으로 대량 생성
