# Backlog 우선순위 → Roadmap 실행 (스킬 3)

두 단계로 나뉜다.

1. **우선순위 제안** — `Backlog.md` 전 항목에 우선순위를 붙이고 사용자 확인을 받는다.
2. **Roadmap 실행** — 사용자가 **진행하겠다고 확인한** 항목만 `Roadmap.md`에 넣고, **한 번에 하나** 구현하며 날짜를 기록한다.

## 파일

| 파일 | 역할 |
|------|------|
| `Backlog.md` | 전체 백로그 (소스). 확인된 항목은 상태만 갱신하고 내용은 남긴다. |
| `Roadmap.md` | 합의된 진행 목록 + 체크·날짜. 없으면 생성. |

## 우선순위 스케일

| 코드 | 의미 |
|------|------|
| P0 | 막히면 제품/배포에 바로 영향 |
| P1 | 가까운 마일스톤에 넣는 핵심 |
| P2 | 중요하지만 미룰 수 있음 |
| P3 | 아이디어·나중 |

제안 시 각 항목에 **한 줄 이유**를 붙인다 (의존성, 사용자 노출, 위험).

## 1단계 — 우선순위 제안 (확인 전)

1. `Backlog.md`를 읽는다 (가능하면 enrich된 구조).
2. 모든 기능에 P0~P3를 제안한다. 파일을 직접 고쳐 `우선순위: P1` 필드를 넣어도 된다.
3. **구현은 시작하지 않는다.**
4. 사용자에게 표로 보여 주고, **어떤 항목을 이번 Roadmap에 넣을지** 확인을 요청한다.
5. 「전부 해」「P0만」등 확인이 오기 전에 Roadmap에 넣거나 코딩하지 않는다.

## 2단계 — Roadmap.md 작성 (확인 후)

사용자가 진행 목록을 확인하면:

1. `Roadmap.md`가 없으면 아래 템플릿으로 만든다.
2. 확인된 항목만 Roadmap에 옮긴다 (Backlog에서는 `상태: roadmap` + Roadmap 앵커 링크).
3. 순서는 우선순위 → 의존성 → 사용자 확인 순서를 반영한다.

### Roadmap.md 템플릿

```markdown
# Roadmap

> 확정일: YYMMDD
> 소스: Backlog.md (사용자 확인분)

## Now / Next

### 1. {기능 제목} `P0|P1`
- 상태: todo | doing | done
- Backlog 참조: …
- 수락 기준:
  - [ ] …
- 진행 로그:
  - (예정)

## Later (확정됐지만 순서 뒤)
…

## Done
…
```

## 3단계 — 하나씩 실행

1. Roadmap에서 상태가 `todo`인 **맨 위(또는 사용자가 지정한) 한 항목만** 고른다.
2. 상태를 `doing`으로 바꾸고 시작일 `YYMMDD`를 로그에 적는다.
3. 해당 기능만 구현·검증한다. 범위 밖 Backlog 항목은 건드리지 않는다 (필요하면 backlog-capture로만 추가).
4. 끝나면:
   - 수락 기준 체크
   - 상태 `done`
   - 진행 로그에 `완료 YYMMDD — 요약`
   - Backlog 대응 항목 `상태: done (YYMMDD)`
5. 다음 항목으로 넘어가기 전에 사용자에게 짧게 완료 보고한다. 연속 진행 동의가 있으면 다음 1개만 이어서 한다.

## 디자이너 사용자 배려

- 기술 용어만으로 수락 기준을 쓰지 말고, **화면에서 무엇이 달라 보이는지**를 한 줄 포함한다.
- 「이게 끝인지」모호하면 구현 전에 확인 질문을 한다.

## 하지 말 것

- 확인 없이 Backlog 전체를 Roadmap에 밀어 넣기
- 여러 Roadmap 항목을 한 번에 섞어 구현하기
- Done 로그 없이 커밋만 하고 Roadmap을 안 고치기
- 완료 항목을 Backlog에서 삭제하기 (상태는 바꾸되 기록 유지)
